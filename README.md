# trust_prediction

Программа автоматизации **прогнозирования доверия приложения** по
**ГОСТ Р ИСО/МЭК 27034-7-2020** «Информационные технологии. Безопасность
приложений. Часть 7. Основы прогнозирования доверия» (идентичен
ISO/IEC 27034-7:2018, *Assurance prediction framework*).

Не требует внешних библиотек — только стандартная библиотека Python 3.10+.

## Что делает программа

Реализует процесс стандарта как последовательность из **десяти шагов**
(раздел 12.2) поверх модели предметной области стандарта:

* **МОБП** — меры обеспечения безопасности приложений;
* **НСО / НСП** — нормативные структуры организации и приложения;
* **ПОБП (PASR)** — прогнозное обоснование безопасности приложения, с
  шестью обязательными компонентами (п. 9.2);
* три уровня доверия — **фактический**, **ожидаемый**, **целевой**
  (раздел 5);
* **анализ существенности изменений** (раздел 7) — эвристика,
  классифицирующая изменения как существенные / пограничные /
  несущественные и блокирующая прогноз для существенных изменений;
* **двойное независимое утверждение** прогноза группой НСО и владельцем
  приложения (п. 5.5) — ни одна из сторон не может принудить другую;
* **аудит и верификация** ПОБП выборочным повторным выполнением мер
  (разделы 10-11), включая обязательную верификацию критических мер;
* **отчёт об ожидаемом уровне доверия** (раздел 13) — итоговый
  Markdown-документ с полным обоснованием, историей версий и журналом
  процесса.

### Важная оговорка

Эвристика оценки существенности изменений (`trust_prediction/substantiality.py`)
— это вспомогательный инструмент поддержки принятия решений, реализующий
методические ориентиры п. 7.2 стандарта в виде настраиваемой формулы.
Сам стандарт прямо указывает (п. 7.1), что закрытого перечня признаков
существенности не существует, и решение принимается на основе анализа
риска в контексте конкретного приложения. Программа не подменяет этот
анализ, а структурирует, документирует и делает его воспроизводимым;
итоговое решение в любом случае проходит обязательное двойное
утверждение человеком.

## Структура проекта

```
прога/
├── main.py                     — точка входа (python main.py <команда>)
├── trust_prediction/
│   ├── models.py                — доменные сущности и перечисления
│   ├── storage.py               — JSON-репозиторий состояния проекта
│   ├── substantiality.py        — эвристика существенности изменений (раздел 7)
│   ├── raci.py                  — матрица RACI процесса (раздел 9.5, 12)
│   ├── pasr.py                  — построение и утверждение ПОБП (раздел 9)
│   ├── trust.py                 — расчёт уровней доверия (разделы 5, 8)
│   ├── audit.py                 — аудит и верификация ПОБП (разделы 10-11)
│   ├── workflow.py              — оркестрация 10 шагов процесса (раздел 12)
│   ├── report.py                — отчёт об ожидаемом уровне доверия (раздел 13)
│   ├── demo.py                  — сквозной демонстрационный сценарий
│   ├── cli.py                   — интерфейс командной строки
│   ├── webapp.py                — локальный веб-сервер (JSON API + статика)
│   └── static/                  — веб-интерфейс: index.html, style.css, app.js
└── tests/                       — модульные тесты (unittest, без внешних зависимостей)
```

## Графический интерфейс (веб)

Поверх той же логики (`workflow.py`, `report.py`, `raci.py`) есть локальный
веб-интерфейс — карточный дашборд с формами для каждого шага процесса,
матрицей RACI, индикатором уровня доверия и просмотром отчёта прямо в
браузере. Реализован без каких-либо фреймворков и внешних зависимостей:
`trust_prediction/webapp.py` — это `http.server` из стандартной библиотеки,
отдающий статику (`trust_prediction/static/`) и небольшой JSON-API, за
которым стоят те же функции, что вызывает CLI. Веб-интерфейс и CLI
полностью взаимозаменяемы и могут работать с одним и тем же файлом
`project.json`.

```bash
.venv/bin/python main.py web
# откроется http://127.0.0.1:8765/ в браузере по умолчанию

# свой порт / файл проекта / без автооткрытия браузера:
.venv/bin/python main.py web --project data/project.json --port 8080 --no-browser
```

В интерфейсе можно: зарегистрировать приложение и меры (МОБП); задать
политику прогнозирования (шаг 1); создавать версии и изменения с
автоматическим анализом существенности (шаг 3); готовить ПОБП по каждой
мере (шаг 4) и утверждать их двумя независимыми решениями — НСО и
владельцем приложения (шаг 6); фиксировать фактическое выполнение мер
(шаг 7); запускать верификацию выборкой, аудит и итоговую оценку (шаги
8–10); смотреть и скачивать отчёт (раздел 13) и экспортировать
`project.json`. Кнопка «Демо-сценарий» загружает тот же сквозной пример,
что и `python main.py demo`, не трогая ваш собственный проект — из
демо-режима можно в любой момент вернуться к своим данным.

### Выпадающие списки вместо свободного текста

Категория меры, её критичность и все поля-акторы (представитель НСО,
владелец приложения, инициатор, исполнитель, аудитор и т.д. — везде, где
раньше нужно было вводить имя/роль вручную) теперь оформлены как
выпадающие списки. Список акторов собирается автоматически: типовые роли
RACI (Группа НСО, Владелец приложения, Аудитор и т.д.) плюс имена,
которые уже встречались в текущем проекте (владелец приложения,
исполнители, участники аудита). Если нужного варианта нет — в конце
списка есть пункт «Другое (ввести вручную)…», после выбора которого
появляется обычное текстовое поле.

### Отчёт: большая кнопка и PDF

Наверху карточки версии есть крупная кнопка «Получить отчёт» — открывает
тот же просмотр отчёта (раздел 13), что и раньше, но теперь с двумя
вариантами скачивания: **Markdown** (как прежде) и **настоящий PDF**,
формируемый на сервере (кириллица, разметка, таблица разбивки по мерам,
полный журнал — всё как в Markdown-версии, но в файле `.pdf`).

PDF-экспорт — единственная часть программы, которой нужна внешняя
библиотека (остальной код по-прежнему работает без единой зависимости).
Один раз установите её в виртуальное окружение проекта:

```bash
.venv/bin/pip install -r requirements.txt
```

Если библиотека не установлена, кнопка «Скачать PDF» покажет понятное
сообщение с этой же командой вместо того, чтобы упасть с ошибкой —
Markdown-отчёт при этом всегда доступен без каких-либо дополнительных
зависимостей. PDF можно получить и из командной строки:

```bash
.venv/bin/python main.py report --version <id> --format pdf --out report.pdf
```

## Быстрый старт (командная строка)

```bash
# из папки проекта, используя уже созданное виртуальное окружение:
.venv/bin/python main.py demo
```

Команда `demo` прогоняет весь процесс целиком на условном примере —
версия 1.1 «Портала электронного документооборота» прогнозируется на
основе версии 1.0: часть мер (с существенными изменениями кода)
блокируется от прогнозирования и выполняется заново, часть — успешно
переносится через утверждённый ПОБП, одна мера демонстрирует отказ
владельца приложения в утверждении прогноза. Результат — файлы
`demo_run/project.json` (состояние) и `demo_run/report.md` (итоговый
отчёт, раздел 13 стандарта).

Показать референсную матрицу RACI процесса:

```bash
.venv/bin/python main.py raci
```

Запустить тесты:

```bash
.venv/bin/python -m unittest discover -s tests -v
```

## Пошаговое использование через CLI

Все команды пишут состояние в один JSON-файл (`--project`, по умолчанию
`data/project.json`) — его можно посмотреть, отредактировать или
передать коллеге. Опция `--project` указывается **после** имени
команды.

```bash
P=data/project.json

# 0. регистрация приложения и мер обеспечения безопасности
python main.py init --project $P --app "Моё приложение" --owner "Иванов И.И."
python main.py add-control --project $P --name "SAST" --category code --weight 1.5 --critical
python main.py add-control --project $P --name "Ревью доступа" --category access --weight 1.0

# 1. эталонная версия — фактический уровень доверия
python main.py new-version --project $P --label "1.0" --target 0.9
python main.py record-reference --project $P --version <ID_ВЕРСИИ> --control <ID_МЕРЫ> \
    --outcome pass --evidence "отчёт SAST v1.0" --by "Команда"

# 2. новая версия и изменения (раздел 7)
python main.py new-version --project $P --label "1.1" --parent <ID_ВЕРСИИ_1.0> --target 0.85
python main.py add-change --project $P --version <ID_ВЕРСИИ_1.1> \
    --desc "Изменение архитектуры" --category architecture \
    --controls <ID_МЕРЫ1>,<ID_МЕРЫ2> --impact 0.3

# 3. процесс прогнозирования (шаги 1-10 стандарта)
python main.py set-policy    --project $P --policy conditional --actor "НСО"
python main.py analyze       --project $P --version <ID> --actor "Эксперт"
python main.py propose-pasr  --project $P --version <ID> --control <ID_МЕРЫ> \
    --initiator "Команда" --onf "НСО" --owner "Владелец" \
    --circumstances "..." --rationale "..." --criteria "..."
python main.py approve       --project $P --pasr <ID_ПОБП> --party onf   --decision approved --actor "НСО"
python main.py approve       --project $P --pasr <ID_ПОБП> --party owner --decision approved --actor "Владелец"
python main.py execute       --project $P --version <ID> --control <ID_МЕРЫ> --outcome pass --evidence "..." --by "Команда"
python main.py verify        --project $P --version <ID> --actor "Аудитор" --sampling-rate 0.34
python main.py audit         --project $P --version <ID> --actor "Аудитор"
python main.py assess        --project $P --version <ID> --actor "Аудитор"
python main.py report        --project $P --version <ID> --out report.md
python main.py status        --project $P --version <ID>   # то же самое, но в консоль
```

Полный список команд и параметров: `python main.py --help`,
`python main.py <команда> --help`.

## Как это соотносится со стандартом

| Шаг процесса (раздел 12.2) | Метод `workflow.TrustPredictionWorkflow` | Команда CLI |
|---|---|---|
| 1. НСО задаёт методологию | `step1_set_policy` | `set-policy` |
| 2. Инициирование прогноза | `step2_initiate` | (внутри `propose-pasr`) |
| 3. Анализ рисков | `step3_risk_analysis` | `analyze` |
| 4. Подготовка ПОБП | `step4_prepare_pasr` | `propose-pasr` |
| 5. Согласование с владельцем | `step5_coordinate_with_owner` | — (API) |
| 6. Утверждение (двойное) | `step6_approve` | `approve` |
| 7. Выполнение оставшихся МОБП | `step7_execute_control` | `execute` |
| 8. Верификация | `step8_verify` | `verify` |
| 9. Аудит | `step9_audit` | `audit` |
| 10. Отчёт об ожидаемом уровне доверия | `step10_assess` + `report.build_report` | `assess`, `report` |

## Известные ограничения / возможные направления развития

* Числовая модель уровня доверия (взвешенная доля мер) — реализационное
  решение для автоматизации; сам стандарт задаёт уровни доверия
  качественно и не определяет единую шкалу.
* Матрица RACI (`raci.py`) — референсная конфигурация по умолчанию,
  соответствующая ролям и логике разделов 9.5/12 стандарта; для
  конкретной организации её стоит адаптировать под свою НСО.
* Верификация (раздел 11) в текущей версии моделирует результат
  повторного выполнения меры значением, переданным пользователем
  (`--mismatch` в `verify`), а не подключением к реальным инструментам
  сканирования — интеграция с конкретными SAST/DAST/SCA-инструментами
  вынесена за рамки данной автоматизации и является естественным
  следующим шагом.
